# Phase 1: The Bridge — Mesen2 TCP Protocol

## Overview

The bridge connects Mesen2 (NES emulator on Windows) to jeROMy's TypeScript side (the dsh plugin in WSL2) over a TCP socket. The Lua script inside Mesen2 acts as a client, connecting to the TypeScript TCP server that `MesenService` starts on :9001.

```
dsh + jeROMy plugin (WSL2) ←—TCP :9001—→ Lua Client (Windows, Mesen2)
   MesenConnection / MesenAdapter                emu.* API calls
```

## Architecture

**TypeScript side (WSL2)** runs two servers:
- **HTTP + WebSocket** on port 3000 — serves the web UI, proxies browser commands
- **TCP server** on port 9001 — accepts the Mesen2 Lua client

**Lua side (Windows/Mesen2)** is a TCP client:
- Connects to `127.0.0.1:9001` on script load (Windows → WSL2 localhost forwarding)
- Polls for commands each frame via non-blocking `receive()` in `endFrame` callback
- When paused, uses blocking `receive()` with timeout in `codeBreak` callback (see [Emulator Control](#emulator-control-pausestepresume))
- Executes `emu.*` API calls and returns results

### Why this direction?

WSL2's NAT networking forwards Windows `localhost` → WSL2 natively, but WSL2 → Windows requires the host IP. Running the TCP server in WSL2 avoids firewall issues.

## Protocol

Messages are **newline-delimited JSON** over TCP.

### Request (TypeScript → Lua)

```json
{"id": "uuid-here", "method": "screenshot", "params": {}}
```

### Success Response (Lua → TypeScript)

```json
{"id": "uuid-here", "result": {"png_base64": "iVBOR..."}}
```

### Error Response (Lua → TypeScript)

```json
{"id": "uuid-here", "error": "description of what went wrong"}
```

The `id` field is a UUID generated by the TypeScript side for request/response matching. Multiple requests can be in flight concurrently.

### Heartbeat (Lua → TypeScript)

```json
{"heartbeat":true}
```

Sent by the Lua client every ~2 s (120 frames) while connected and running.
It is not a response and the TypeScript side drops it without matching. Its
purpose is detection: a peer that exits without its FIN reaching Windows
(seen 2026-10-05 when a headless dsh run ended) leaves `receive` returning
`timeout` forever, so only a failed `send` reveals the dead socket. The
second heartbeat after the RST fails and the client reconnects within ~4 s.
No heartbeat is sent while paused (`codeBreak` uses blocking receives and
sees the close directly).

### Two-phase (pending) requests

Some handlers need frames to run before they can answer (ADR-0010: the
scroll-write capture; ADR-0009: `trace_writes`). Such a handler returns
`{ pending = { frames = N, complete = fn, cancel = fn, allow_paused = bool } }`
to the Lua dispatcher instead of a result. The dispatcher parks the request
id, sends nothing yet, and answers from a later `endFrame` once `N` frames
have elapsed, with `complete()`'s return value under the original id. On
the wire this is invisible: one request, one response, matched by id; the
TypeScript caller passes a per-request `timeoutMs` sized to the wait.

Rules: completion runs only from `endFrame`, never from the paused
`codeBreak` poll, so it cannot touch the watchdog budget. A pending request
issued while paused is refused at once with an error naming
`resume_emulator`/`step_frame` (frames do not run while paused) unless the
handler sets `allow_paused` and arranges the steps itself. `cancel()` runs
on the 600-frame cap and on disconnect, so a handler's memory callbacks
never outlive its request. `wait_frames {frames}` is the trivial pending
handler kept for verification.

## Emulator Control (Pause/Step/Resume)

**Paused and disconnected** (2026-10-05): `endFrame` does not run while
paused, so the only place a reconnect can happen is the `codeBreak`
callback. When it finds no connection it makes one bounded connect attempt
per second (0.5 s connect timeout, a 0.2 s sleep between keep-alive steps)
and steps one instruction so it is called again. A drop detected inside
the blocking poll also issues the keep-alive step before returning; without
it Mesen would sit paused with no callback ever firing, which is how a
headless run that ended while paused used to leave the bridge unreachable.

The bridge supports pausing, stepping, and resuming the emulator. This is critical for batch editing workflows — the agent can pause the game, make multiple edits, step forward to render the changes, take a screenshot to verify, and then resume.

### The Polling Problem

Mesen2's Lua API only runs code inside callbacks. The `endFrame` callback fires every frame (~60fps) while the game is running, so TCP commands are processed there. But when the emulator is **paused**, `endFrame` stops firing — and there's no way to process incoming commands.

### Solution: Blocking TCP Receive in codeBreak

When the emulator breaks (via `pause_emulator` or the Mesen UI), the `codeBreak` callback fires. Inside this callback, the bridge:

1. Switches the socket to **blocking mode** with a 200ms timeout (`conn:settimeout(0.2)`)
2. Calls `poll_connection()` up to 3 times (600ms total), processing any commands that arrive
3. If a `resume_emulator` command arrives, calls `emu.resume()` and returns
4. If a `step_frame` command arrives, calls `emu.step(1, emu.stepType.ppuFrame)` and returns
5. If nothing arrives, issues a keep-alive `emu.step(1, emu.stepType.step)` to schedule the next `codeBreak`

The 600ms budget stays safely under Mesen2's **1-second Lua watchdog timer** (ScriptTimeout), which kills scripts that take too long. The blocking `socket.receive()` call uses the OS-level `select()` system call, which doesn't consume CPU or count as Lua instructions — but the elapsed wall-clock time is still checked by the watchdog when Lua resumes.

Each `codeBreak` invocation gets a fresh 1-second budget, so the bridge can remain paused indefinitely — each callback does ~600ms of blocking receives, then schedules the next callback via `emu.step()`.

### State Tracking

- `is_paused` — semantic pause state (true when paused via our tool OR Mesen UI)
- `step_active` — prevents `endFrame` from clearing `is_paused` during a step transition
- `pending_steps` / `pending_resume` — flags set by handlers, consumed in `codeBreak`

External resume detection: if the user resumes via Mesen's own UI, `endFrame` fires with `step_active = false` and `is_paused = true` — the bridge detects this and clears `is_paused`.

## Palette Freezing

NES games rewrite palette RAM every frame during VBlank. A one-shot `write_palette` would be overwritten in ~16ms. The bridge maintains a `palette_overrides` table — when a palette color is written, the override is stored and re-applied every frame in the `endFrame` callback. Use `clear_palette_overrides` to unfreeze individual entries or all at once.

## Memory Type Resolver

Mesen2 builds vary in how `emu.memType` entries are named. Some use short names (`palette`, `ppuDebug`, `cpuDebug`), others use NES-prefixed names (`nesPaletteRam`, `nesPpuDebug`, `nesDebug`). The bridge resolves the correct names once at startup using `resolveMemType()`, which tries NES-prefixed names first, then falls back to legacy short names. The resolved values are stored in an `MT` table used by all handlers. This is logged at startup so you can verify which names were found.

## Log Buffer

The bridge wraps `emu.log()` to also store messages in a ring buffer (200 entries max). The `get_lua_logs` method returns buffered entries since a given Unix timestamp, allowing the browser to fetch and include Lua-side logs in exports.

## Mesen2 Lua API Notes

### emu.getState()

Returns a **flat table** with dot-separated string keys, NOT nested tables:

```lua
local state = emu.getState()
-- Access as: state["ppu.xScroll"], state["cpu.a"], state["ppu.control.largeSprites"]
-- NOT: state.ppu.xScroll (this is nil)
```

### emu.takeScreenshot()

Returns raw PNG binary data as a Lua string. Must be base64-encoded for JSON transport.

### emu.read / emu.write

```lua
emu.read(address, emu.memType.ppuDebug)  -- read a byte
emu.write(address, value, emu.memType.palette)  -- write a byte
```

**Note:** `emu.memType` names vary by Mesen2 build. Some builds use `emu.memType.palette` while others use `emu.memType.nesPaletteRam`. The bridge resolves these automatically at startup — see "Memory Type Resolver" above.

### emu.getRomInfo()

Returns a normal Lua table (not flat): `{name, path, fileSha1Hash, format}`.

## Running

1. `scripts/up.sh` (WSL2): starts dsh with the plugin, launches Mesen2 with the ROM and `mesen/bridge.lua`, waits for the connection
2. Or by hand: start dsh, then load `mesen/bridge.lua` in Mesen2 (Tools → Script Window → Open → Run)
3. `curl http://127.0.0.1:9002/status` shows `connected:true`
